## 1. Executive Summary

- **Czy projekt się uruchamia?** **POTWIERDZONE — TAK**, w środowisku z zainstalowanymi zależnościami Python (`pip install -r requirements.txt`) i Node (`npm install` w `cockpit/`). `python3 -c "import aihub.main"` kończy się sukcesem (`IMPORT_OK`, zob. §37). `uvicorn aihub.main:app` ma kompletny `lifespan` (init DB, load knowledge graph, start agent worker, start consolidation worker, wiring memory/psyche) — `aihub/main.py:134-169`. Brak w repo realnych sekretów (`LLM_API_KEY`, `BRAVE_API_KEY`, `VOYAGE_API_KEY`) oznacza, że po starcie **backend odpowiada na HTTP**, ale ścieżki wymagające LLM/embeddingów zdalnych/web-search **nie zwrócą realnych wyników** bez skonfigurowanych kluczy — potwierdzone przez `GET /ops/ready` → `503`, `blocking: [{"layer":"llm","status":"error"}]` (log testu `test_functional_endpoint_smoke`, §37).
- **Czy backend działa?** **POTWIERDZONE (częściowo, zależnie od konfiguracji)** — FastAPI startuje, 97 tras HTTP (9 zamontowanych routerów + ~30 inline w `main.py` + auto-trasy FastAPI), 962/963 testów jednostkowych/integracyjnych przechodzi (1 fail = brak `LLM_API_KEY` w tym środowisku, nie błąd kodu; 1 skip = brak zewnętrznego skryptu). Deterministyczny fallback embeddingów (`AIHUB_DETERMINISTIC_EMBEDDING_FALLBACK`) pozwala testom przejść bez sieci.
- **Czy frontend działa?** **POTWIERDZONE — TAK.** `npm run typecheck` → 0 błędów. `npm run lint` → 0 ostrzeżeń/błędów. `npm run test` (vitest) → 66/66 testów zielone. `npm run build` (`next build`) → sukces, 4 trasy wygenerowane (`/`, `/user`, `/_not-found`, `/api/aihub/[...path]`). Wymaga działającego backendu pod `AIHUB_BASE_URL` do realnej pracy (BFF proxy).
- **Czy główny czat działa?** **DZIAŁA CZĘŚCIOWO (potwierdzone architektonicznie, częściowo BRAK DANYCH bez sieci/kluczy).** `POST /chat/turn` → `ChatRuntime.run_turn()` (`aihub/chat_api.py`, `aihub/chat_runtime.py`) ma kompletny, jednoznaczny pipeline: walidacja → strategy_selector → psyche read → memory read (context pack) → opcjonalny web prefetch/tool-calling → budowa system promptu → wywołanie LLM (DeepInfra) → parsowanie odpowiedzi → zapis pamięci (V1+V2) → zapis psyche (V1+V2) → zdarzenia SSE/`event_log`. Cały ten łańcuch jest **realnie zaimplementowany i pokryty testami** (m.in. `tests/test_chat_runtime.py`, 37,8 KB testów). Realna odpowiedź od modelu wymaga `LLM_API_KEY`/`DEEPINFRA_API_KEY` — **BRAK DANYCH DO POTWIERDZENIA** w tym środowisku (brak klucza, brak dostępu do sieci zweryfikowanego w tym audycie).
- **Czy Memory Engine działa?** **DZIAŁA** w warstwie kanonicznej: zapis trwały do SQLite/Postgres (`aihub/db/runtime.py`), FAISS on-disk (`aihub/vector_engine.py`), embeddingi realne (Voyage / SentenceTransformers / deterministic-hash fallback), izolacja per `user_id` w warstwie V2 i grafie v1. Odczyt trafia do promptu (3 kanały wstrzykiwania — §7). Ma jednak realne dziury: `run_decay_pass` niewpięty do schedulera, `meta_memory` bez filtra `user_id` (ryzyko cross-user), cały pakiet `aihub/memory/` (5 plików) i 3 routery HTTP martwe (niezamontowane), błąd w `MemoryV2Service.reinforce_memory()` (`memory_v2_service.py:564-565`).
- **Czy Psyche Engine działa?** **DZIAŁA CZĘŚCIOWO** — dual model V1 (mood/energy/focus, SQLite `psyche_state`) + V2 (profile/state/habits/relations, SQLite `psyche_v2_*`), obie warstwy realnie czytane i zapisywane co turę, obie wpływają na prompt (`psyche_layer` w `_build_system_prompt`). Brakuje: automatycznej refleksji V2 (`reflect_user` tylko on-demand HTTP), habit decay (zdefiniowany, nigdy schedulowany), `dreams`/`introspection` (brak implementacji), `nervous_system`/`anomaly_detector` (niewpięte workery), cały legacy pakiet `aihub/psyche/` (martwy) i 5 routerów HTTP „psyche brain”/„predict” (niezamontowane — to inny, niepowiązany system: anomaly detection HTTP, nie „psychika”).
- **Czy Web działa?** **DZIAŁA** — web jest realnie osiągalny z głównego czatu (heurystyczny `web_decision` w `strategy_selector.py` + deterministyczny prefetch + opcjonalny LLM tool-calling), ma realną ochronę SSRF (`web_tools.py::validate_url_safe`), realny Brave Search HTTP (wymaga `BRAVE_API_KEY`), realny fetch+parsowanie HTML, i realny zapis do pamięci (`ingest_fact`). Ograniczenia: Brave zwraca tylko snippety (nie pełne strony), brak globalnej deduplikacji multi-backend, `web.ingest_url` niewidoczne w trybie `chat` (tylko `agent`/`debug`), cache 300s ma błąd (`total_results:0` przy hit).
- **Czy dane są trwałe?** **POTWIERDZONE — TAK** dla głównego stosu (SQLite plik na dysku / PostgreSQL, FAISS index na dysku, Vault w SQLite z Fernet). **NIE** dla: `MetricsEngine` (in-memory, TTL 1h), `sse/bus.py::EventBus` (in-memory, ale i tak martwy kod), `nervous_system.blocked` (in-memory, worker i tak nieaktywny).
- **Czy system nadaje się do produkcji?** **NIE w obecnej postaci** — `ENV=production` ma fail-fast na brakujące sekrety (dobra praktyka), ale: (a) brak CI/CD (`.github/workflows` nieobecne), (b) brak Dockerfile/docker-compose, (c) brak connection poolingu SQLite (nowe połączenie per operacja), (d) 11 legacy routerów HTTP z kolizjami prefiksów pozostaje w drzewie `aihub/api/` (ryzyko przypadkowego zamontowania), (e) `MetricsEngine`/`sse/bus.py` i 4 workery (`adaptive_learning`, `anomaly_detector`, `auto_train_worker`, `nervous_system`) — niewpięte, dają złudzenie funkcjonalności, (f) domyślny streaming SSE jest atrapą (pseudo-chunking) gdy `LLM_STREAMING_ENABLED=0` (wartość domyślna).
- **Realny procent ukończenia projektu:** **~68/100.** Uzasadnienie: architektura jest spójna i w większości zrealizowana (nie fasada — realne zapisy, realne odczyty, realne testy przechodzące), kod importuje się i testy przechodzą (962/963), frontend buduje się bez błędów. Punkty ujemne: istotne martwe/niewpięte fragmenty (2 całe legacy pakiety, 11 nieaktywnych routerów, 4 nieaktywne workery, atrapa streamingu domyślnie), brak CI/CD i konteneryzacji, ryzyka izolacji użytkowników w `meta_memory`, brak automatycznej konsolidacji dla wszystkich mechanizmów pamięci/psychiki (decay, habit decay), brak testów E2E względem prawdziwego LLM w tym środowisku (BRAK DANYCH — wymaga kluczy).

## 4. Architektura rzeczywista

Architektura wynikająca z kodu (nie z README) to **monolit FastAPI** (`aihub/`) + **oddzielny frontend Next.js** (`cockpit/`) komunikujący się wyłącznie przez BFF proxy (`cockpit/app/api/aihub/[...path]/route.ts`), bez bezpośredniego wywołania backendu z przeglądarki (brak CORS w backendzie — nie jest potrzebny, bo przeglądarka mówi tylko z Next.js serwerem).

```

│  Przeglądarka (React 19, Next.js 15 App Router)                     │
│  Aktywny UI: UserShell (/, /user)  |  Martwy UI: AppShell (nigdzie) │
└───────────────────────────────┬───────────────────────────────────────┘
                                 │ fetch("/api/aihub/...")
                                 ▼
┌─────────────────────────────────────────────────────────────────────┐
```

## 5. Entrypointy i proces uruchomienia

### Backend

- **Entrypoint:** `uvicorn aihub.main:app` (`aihub/main.py:937-944`, wołane też przez `start.sh:488-492`).
- **Wymagana komenda (minimalna):** `pip install -r requirements.txt && uvicorn aihub.main:app --host 127.0.0.1 --port 8080`.
- **Skrypt operacyjny:** `./start.sh` — instaluje zależności Python (venv) + npm (cockpit), waliduje env (`ensure_backend_env`), rozgrzewa embeddingi (`warm_embedding_runtime`), uruchamia `scripts/doctor.py` (preflight), startuje backend + frontend, robi health-check (`/system/ping`, `/user`).
- **Wymagane usługi zewnętrzne (do pełnej funkcjonalności, nie do samego startu):**
  - LLM: DeepInfra (`LLM_API_KEY`/`DEEPINFRA_API_KEY`) — bez tego chat nie wygeneruje realnej odpowiedzi modelu.
  - Embeddingi: Voyage AI (`VOYAGE_API_KEY`) — bez tego fallback do SentenceTransformers (jeśli `AIHUB_ALLOW_EMBEDDING_PROVIDER_FALLBACK=1`) lub deterministic-hash (testy).
  - Web search: Brave Search (`BRAVE_API_KEY`) — bez tego `research.query` zwraca pusty wynik (chyba że `AIHUB_ENABLE_OPTIONAL_RESEARCH_BACKENDS=1` — Wikipedia/DDG).
  - PostgreSQL — **opcjonalne**, tylko gdy `DB_BACKEND=postgres`; domyślnie SQLite (plik lokalny, brak zewnętrznej usługi).
  - Ollama — opcjonalne, tylko dla wizji obrazków (`CHAT_VISION_BACKEND=ollama`).
- **Wymagane zmienne środowiskowe (start minimalny w dev):** żadne nie są ściśle wymagane do startu w `ENV=development` — `_validate_production_secrets()` (`aihub/config.py:102-145`) jest wołane tylko przy `ENV=production`. Potwierdzone: `python3 -c "import aihub.main"` przeszło bez żadnych zmiennych env poza domyślnymi (§37).
- **Port domyślny:** `8080` (`HOST=127.0.0.1`, `.env.example:19-20`).
- **Wykryte problemy startowe:**
  1. `_wire_memory_psyche_into_runtime()` i `start_background()` są w `try/except` łapiącym `Exception` z tylko `logger.warning` — backend **wstaje nawet gdy worker konsolidacji nie wystartuje** (`aihub/main.py:146-149`) — cichy błąd operacyjny.
  2. Brak jawnego `.env` w tym repo (tylko `.env.example`) — pierwszorazowy `git clone` + `uvicorn aihub.main:app` bez `cp .env.example .env` uruchomi się (bo `ENV=development` domyślnie i sekrety nie są wymagane), ale z pustymi kluczami LLM/Brave/Voyage — cichy start "połowicznie działającego" systemu bez ostrzeżenia poza logiem `WARNING` przy pierwszym wywołaniu LLM.
  3. `AIHUB_USER_VAULT_KEY` — wymagany w `ENV=production`, ale **nie jest wymieniony w `.env.example`** (potwierdzone `grep -n "VAULT_KEY" .env.example` → 0 wyników, §37) — operator przełączający na produkcję bez znajomości kodu nie odkryje tej zmiennej z przykładowego pliku env.

| Streaming realny | **DZIAŁA CZĘŚCIOWO** | Realny token-by-token TYLKO gdy `LLM_STREAMING_ENABLED=1` I brak tool calls; domyślnie (`=0`) → **ATRAPA** — pseudo-chunking po fakcie (`chat_api.py:151-156`, sleep 12ms/chunk) |
| Limity tokenów (`max_tokens`) | **BRAK IMPLEMENTACJI** w runtime | Pole istnieje w `ProviderChatRequest`, ale `_provider_call` (`chat_runtime.py:4649-4654`) go nie ustawia — używany jest default API |
| Tool calling / function calling | **DZIAŁA** | `_build_provider_tools()` (`chat_runtime.py:4623-4632`), whitelist per strategia |
| Kolejność promptu | **DZIAŁA (zgodna z dokumentacją)** | `chat_context_compose.py:5-15` + implementacja `_build_system_prompt` (`chat_runtime.py:1182-1203`): anti-hallucination → system rules → product rules → execution rules → psyche → memory → correction → web policy → capabilities |
| Wstrzykiwanie pamięci | **DZIAŁA** | `memory_layer` w prompt (§7) |
| Wstrzykiwanie psyche | **DZIAŁA** | `psyche_layer` w prompt (§8) |
| Wstrzykiwanie wyników web | **DZIAŁA** | Prefetch jako `assistant`+`tool` messages przed ostatnim `user` message |
| Propagacja błędów LLM | **DZIAŁA (kontrolowana degradacja, nie fałszywy sukces)** | `ProviderError` → `result.ok=False` + fallback text (`chat_runtime.py:5759-5769`); nieoczekiwane wyjątki propagują (`4869-4871`) |
| Blokowanie event loop | **NIE WYKRYTO** w ścieżce czatu | Wszystkie klienty HTTP w ścieżce LLM/web są async (`httpx.AsyncClient`); sync HTTP w `research_engine` owinięte w `asyncio.to_thread` |
| Koszty/telemetria | **BRAK IMPLEMENTACJI** trwałej | Brak liczników kosztów tokenów per-user w trwałym storage (tylko trace per-request) |

**Wnioski:** LLM orchestration jest **scentralizowana i realna** (jeden provider, jeden punkt wywołania), ale ma 3 istotne luki produkcyjne: brak multi-provider fallback, brak `max_tokens` w runtime (ryzyko niekontrolowanych kosztów/długości odpowiedzi), i domyślnie wyłączony realny streaming (frontend dostaje pseudo-chunki, nie żywe tokeny modelu) — co jest zgodne z kodem frontendu (`chat-turn-stream.ts` realnie parsuje SSE, ale to backend decyduje czy wysyła prawdziwe delty czy end-of-turn chunking).

### Middleware / lifecycle

## 24. Problemy obserwowalności

- **Logi:** plikowe (`LOG_DIR=logs`, `LOG_LEVEL=INFO`), konfigurowane w `aihub/core/logging.py`. Format standardowy Python `logging`. **Brak** strukturyzowanego JSON logging, **brak** korelacji request-id między logami różnych modułów (poza `event_log` w DB per-user).
- **Metryki:** `MetricsEngine` — **in-memory, nietrwałe**, TTL 1h, restart procesu = utrata historii. Brak eksportu do Prometheus/StatsD/OpenTelemetry.
- **Trace/APM:** brak jakiegokolwiek APM (Sentry, DataDog, OpenTelemetry). Istnieje wewnętrzny `ops_trace.py` i pola `trace` w `ChatTurnResult` — to jest **diagnostyka per-request w response**, nie system trace rozproszony.
- **Health-checki:** `GET /ops/health` i `GET /ops/ready` są **realne, wielowarstwowe** (nie stub) — sprawdzają DB, memory v1/v2, embeddingi, vector, LLM (konfiguracja + opcjonalny live probe), vision/STT, psyche, web. To jest **mocny punkt** obserwowalności.
- **`/system/ping`** to czysty liveness (stały JSON) — **nie** sprawdza żadnej zależności, co jest poprawnym wzorcem (liveness ≠ readiness), ale trzeba to rozumieć przy konfiguracji orchestratora (np. Kubernetes) — użycie `/system/ping` jako readiness probe dałoby fałszywy "zdrowy" status przy zerwanej bazie danych.
- **Alerting:** **BRAK IMPLEMENTACJI** — brak jakiegokolwiek mechanizmu wysyłania alertów (email/Slack/PagerDuty) przy błędach krytycznych. `logger.error`/`logger.warning` to jedyna forma sygnalizacji, wymagająca aktywnego monitorowania logów.
- **`SSE_MAX_EVENT_LOG`** — zmienna zdefiniowana w `.env.example` i `config.py`, ale **nieużywana w kodzie** — sugeruje planowaną, niezaimplementowaną funkcję pruningu `event_log` — ryzyko nieograniczonego wzrostu tabeli `event_log` w czasie.
- **Brak dashboardu metryk** dla operatora poza Cockpit `AppShell` (który jest martwy UI, §12, §15) — realny wgląd w stan systemu ograniczony do wywołań HTTP `/ops/health` bezpośrednio.

## 28. Funkcje realnie działające

(Potwierdzony pełny przepływ: wejście → logika → zapis/odczyt → wpływ na odpowiedź)

- `POST /chat/turn` — pełny pipeline czatu (strategy → psyche → memory → web → LLM → response → zapis).
- Zapis i odczyt pamięci V1 (STM/L1/L2, FTS, TF-IDF rerank) — `memory_engine.py`.
- Zapis i odczyt pamięci V2 (items, hybrid search, consolidation, forgetting sweep) — `memory_v2_service.py`.
- Generowanie i przechowywanie embeddingów (Voyage/ST/deterministic) — `embedding_engine.py`.
- FAISS init/search/save/load po restarcie — `vector_engine.py`.
- Psyche V1 (mood/energy/focus) — read+write co turę, wpływ na prompt i strategy.
- Psyche V2 (profile/state/habits/relations) — read+write, wpływ na behavior_instructions w prompcie.
- Post-action reflection (`reflection_engine.py`) — per turę, zapis do `reflections`, odczyt przez `PolicyEngine`.
- Strategy selection (`strategy_selector.py`) — deterministyczna, moduluje ścieżkę wykonania co turę.
- Web prefetch + tool-calling web/research — realny HTTP, realny SSRF-guard, realny zapis do pamięci.
- LLM orchestration (DeepInfra) — retry, timeout, kontrolowana degradacja błędów.
- Auth middleware (gdy skonfigurowane sekrety) — blokuje nieautoryzowany dostęp.
- `/ops/health`, `/ops/ready` — realne, wielowarstwowe health-checki.
- Agent worker (background, thread) — realny cykl agentowy z retry/backoff.
- Consolidation worker (background, thread) — realna konsolidacja/forgetting Memory V2.
- Frontend: streaming SSE (gdy backend faktycznie streamuje), upload plików, historia sesji, BFF proxy z allowlist i bezpiecznym wstrzykiwaniem klucza.
- Vault (szyfrowanie sekretów usera, Fernet) — realny zapis/odczyt z izolacją per-user.
- SSRF protection dla `web.fetch_url` — realna, wielopoziomowa walidacja.

## 29. Funkcje działające częściowo

- Hybrid search V2 (dense+lexical+priority) — realna fuzja, ale lexical to `LIKE`, nie BM25.
- Web research (`research.query`) — realny HTTP, ale Brave zwraca snippety, nie pełne strony; cache ma bug.
- Streaming LLM — realny tylko gdy `LLM_STREAMING_ENABLED=1` i brak tool calls (domyślnie OFF).
- Psyche V2 habits — reinforce działa, decay nie.
- Goal/planner na standardowym chacie — tylko odczyt aktywnych celów, pełny cykl (create→plan→execute) tylko na ścieżce agent handoff.
- `meta_memory` — działa, ale bez izolacji `user_id`.
- Vision/STT (obraz/mowa) — kod kompletny, ale zależny od zewnętrznych backendów (Ollama/whisper) nieprzetestowanych w tym audycie.
- Consistency/simulation engines — realne, ale warunkowo aktywowane (nie każda tura).

## 30. Funkcje niewpięte

- `memory_v2_decay.py::run_decay_pass`.
- `psyche_v2_habits.py::decay_habits`.
- `psyche_v2_service.py::reflect_user` (automatyczny, nie on-demand).
- `cognitive_controller.py`, `planner_engine.py`, `reasoning_engine.py` — w standardowym chacie (aktywne tylko agent handoff).
- `web_tools.py::ingest_url` w trybie `chat`.
- `workers/adaptive_learning.py`, `anomaly_detector.py`, `auto_train_worker.py`, `nervous_system.py`.
- `aihub/middleware/firewall.py`, `recorder.py`.
- 10 legacy routerów HTTP w `aihub/api/*.py`.
- `cockpit` `AppShell` (operator UI, 22 panele) — brak route.
- `cockpit` `StoreRehydrator` — brak montażu.

## 31. Funkcje będące atrapami

- Domyślny streaming SSE w chacie (`LLM_STREAMING_ENABLED=0`) — pseudo-chunking po fakcie.
- `memory_gc.py::schedule_gc` — tylko log, brak logiki.
- Cache research przy hit — zwraca `total_results:0` (fałszywy negatywny sygnał).

## 32. Brakujące elementy

- Dreams / introspection — brak jakiejkolwiek implementacji.
- Multi-provider LLM fallback (tylko jeden provider — DeepInfra).
- `max_tokens` w runtime LLM call.
- Globalny rate limiting HTTP.
- CI/CD (`.github/workflows`), Dockerfile, docker-compose.
- Trwały storage metryk (APM/Prometheus/OpenTelemetry).
- Alerting (email/Slack/PagerDuty) na błędy krytyczne.
- Globalna deduplikacja wyników web search multi-backend.
- Framework migracji DB (Alembic/Flyway) — obecnie ad-hoc ADD COLUMN.
- Connection pooling SQLite.
- Dokumentacja `AIHUB_USER_VAULT_KEY` w `.env.example`.
- `pytest-asyncio` w `requirements.txt`.

## 35. Rekomendowana architektura docelowa

Nie proponuje się wycinania funkcjonalności ani tworzenia nowych duplikatów. Rekomendacja polega na **formalizacji tego, co kod już sam sobie zadeklarował** (bannery `_LEGACY.md`, `ACTIVE_CONFIRMED`) poprzez fizyczne odseparowanie kodu nieaktywnego od aktywnego, analogicznie do już wykonanej archiwizacji `archive/legacy_routers/`:

1. **Warstwa aktywna (bez zmian funkcjonalnych):** `aihub/main.py` + `*_api.py` (9 zamontowanych routerów) + `memory_core`/`memory_engine`/`memory_v2_*` + `psyche_core`/`psyche_engine`/`psyche_v2_*` + `aihub.db` (pakiet) + `chat_runtime.py` + `strategy_selector`/`executive_controller`/`goal_engine`/`reflection_engine` + `web_tools`/`research_engine` + `llm/*` + `workers/agent_worker.py`+`consolidation.py`.
2. **Warstwa archiwalna (przenieść do `archive/`, zachowując pełną historię i możliwość odtworzenia — nie usuwać):** `aihub/memory/*.py`, `aihub/psyche/service.py`+`policy.py`, 10 routerów `aihub/api/*.py` (poza `security_router.py`, `self_heal_status_router.py`), `aihub/middleware/firewall.py`+`recorder.py`, `aihub/services/predictor.py`+`self_rewriter.py`+`events.py`+`memory_intel.py`, `aihub/workers/adaptive_learning.py`+`anomaly_detector.py`+`auto_train_worker.py`+`nervous_system.py`, `aihub/sse/bus.py`. To usunie ryzyko przypadkowego importu/montażu bez utraty ani jednej linijki kodu (analogicznie do tego, jak `ai_compat_router.py`/`ops_router.py`/`admin_router.py` zostały już przeniesione).
3. **Cykl życia pamięci/psychiki — domknięcie pętli:** wpiąć `run_decay_pass` i `decay_habits` jako kolejne kroki w istniejącym `workers/consolidation.py` (worker już działa i już iteruje po użytkownikach — naturalne miejsce rozszerzenia bez tworzenia nowego workera).
4. **Frontend — jedna decyzja produktowa:** albo przywrócić route dla `AppShell` (operator dashboard) jako np. `/cockpit` chronione dodatkową autoryzacją operatorską, albo formalnie oznaczyć `features/` operatorskie jako referencyjne/do usunięcia w przyszłej wersji — obecny stan (kod istnieje, ale jest niedostępny) jest najgorszym z kompromisów (koszt utrzymania bez korzyści UX).
5. **Bezpieczeństwo:** wprowadzić explicit "insecure mode" flag wymaganą do uruchomienia bez auth w dev (zamiast domyślnego fail-open), oraz uzupełnić `.env.example` o `AIHUB_USER_VAULT_KEY` z komentarzem generacji (`python -c "import secrets; print(secrets.token_urlsafe(32))"`).
6. **Operacyjne:** dodać `.github/workflows/ci.yml` (lint+typecheck+test backend i frontend na każdym PR) oraz `Dockerfile`/`docker-compose.yml` (backend + frontend + opcjonalny postgres) — bez zmiany logiki aplikacji, czysto operacyjne domknięcie procesu wdrożenia.

Taka rekonstrukcja nie usuwa żadnej wartościowej funkcjonalności (cała logika legacy jest zachowana w `archive/`, tak jak już zrobiono z trzema routerami), a jednocześnie eliminuje największe ryzyko operacyjne wykryte w tym audycie: przypadkowe użycie nieaktywnej, równoległej implementacji.

## 38. Ostateczne podsumowanie

1. **Co realnie działa?** Cały główny pipeline czatu (walidacja → strategy → psyche → memory → web → LLM → response → zapis), Memory Engine kanoniczny (V1+V2, trwały, z embeddingami i FAISS), Psyche Engine dual V1+V2 (trwały, wpływający na prompt), Web/search wpięty w chat z realnym SSRF-guard, LLM orchestration scentralizowana (DeepInfra), 97 endpointów HTTP (z czego zdecydowana większość realnie funkcjonalna, nie diagnostyczna), frontend `UserShell` (kompletny UI produkcyjny, buduje się i testuje bez błędów), auth middleware (gdy skonfigurowane sekrety), Vault szyfrowania, 2 background workery (agent + consolidation), health-checki wielowarstwowe.

2. **Co jest atrapą?** Domyślny streaming SSE w czacie (pseudo-chunking po fakcie, nie żywe tokeny — dopóki `LLM_STREAMING_ENABLED=0`, wartość domyślna), `memory_gc.py::schedule_gc` (sam log, brak logiki), cache research przy hit (fałszywy `total_results:0`).

3. **Co jest martwe?** Cały pakiet `aihub/memory/*.py` (5 plików), `aihub/psyche/service.py`+`policy.py`, 10 routerów HTTP w `aihub/api/*.py` (memory_router, memory_stats_router, memory_train_router, psyche_router, psyche_brain_router, psyche_brain_live_router, psyche_predict_router, anomaly_router, fs_router, sse_router), `aihub/middleware/firewall.py`+`recorder.py`, `aihub/sse/bus.py`, `aihub/services/predictor.py`+`self_rewriter.py`+`events.py`+`memory_intel.py`, `chat_runtime.py::_run_etap9_cognitive`, RCE/systemctl/admin-leak w `archive/legacy_routers/*.py` (fizycznie już poza pakietem — zneutralizowane), cockpit `AppShell` + 22 panele operatorskie (brak route).

4. **Co jest niewpięte?** `memory_v2_decay.py::run_decay_pass`, `psyche_v2_habits.py::decay_habits`, `psyche_v2_service.py::reflect_user` (auto), `cognitive_controller.py`/`planner_engine.py`/`reasoning_engine.py` w standardowym chacie, `web_tools.py::ingest_url` w trybie chat, 4/6 workerów tła (`adaptive_learning`, `anomaly_detector`, `auto_train_worker`, `nervous_system`), `cockpit` `StoreRehydrator`.

5. **Co blokuje uruchomienie?** Nic krytycznego — **backend i frontend uruchamiają się i działają** po `pip install -r requirements.txt` i `npm install`, bez żadnych sekretów wymaganych w `ENV=development` (wartość domyślna). Jedyne środowiskowe niedogodności potwierdzone w tym audycie: brak `python3.12-venv` w tym konkretnym obrazie systemowym (obejście: `--break-system-packages` lub inny mechanizm izolacji) i brak `pytest-asyncio` w `requirements.txt` (obejście: `pip install pytest-asyncio` manualnie).

6. **Co blokuje produkcję?** Brak CI/CD i konteneryzacji, auth fail-open w dev, brakujący `AIHUB_USER_VAULT_KEY` w dokumentacji env, obecność 10+ legacy routerów/pakietów w drzewie importowalnym (ryzyko operacyjne), brak connection poolingu DB, brak `max_tokens` w LLM call, brak globalnego rate limitingu, 6 nieprzeanalizowanych podatności npm, niewpięte mechanizmy cyklu życia pamięci/psychiki (decay).
