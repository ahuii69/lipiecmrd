## 1. Graf providerów (kanoniczny)

```
POST /chat/turn
  → ChatRuntime
  → ChatTurnApplicationService
  → TurnOps
  → ProviderExecutionService.execute()   ← JEDYNY failover loop
       1. primary: deepinfra (LLM_PRIMARY_PROVIDER)
       2. reserve: groq / openai/gpt-oss-120b (LLM_RESERVE_PROVIDER, GROQ_MODEL)
       3. dry fallback dopiero gdy oba padną (execution._provider_failure_fallback)
```

Potwierdzenia w kodzie:
- jeden failover loop: `aihub/turn/provider_service.py`
- Groq nie startuje równolegle — sekwencyjna pętla `providers_to_try`
- reserve tylko po `is_failover_eligible(exc)` (402 → tak)
- permanentny 4xx requestu (np. invalid payload) → brak bezsensownego retry loop
- executive controller **nie** jest uruchamiany po błędzie providera (usunięte z `execution.py`)
- trace: `provider_attempts[]`, `provider_failover_happened`, final `provider`/`model`

## 3. Reguły retry / failover

| Błąd primary | Retry primary | Failover Groq |
|--------------|---------------|---------------|
| 401, 402, 403 | 0 | tak |
| 408, 429, 5xx, timeout | max 1 | tak |
| malformed / empty content | 0 | tak |
| permanent 4xx (invalid request) | 0 | nie (jeśli nie eligible) |

Twardy limit: `provider_max_attempts` + max 1 retry przed failover (policy).
