## 5. Maskowanie vs degradacja (szczera klasyfikacja)

### 5.1 Maskowanie (źle) — naprawione lub ograniczone

| Pattern | Status |
|---------|--------|
| `str(dict)` runtime context → `response_text` | **NAPRAWIONE** (extract + raise non-text) |
| Post-hoc scrub historii / coerce po polach `system_context` | **USUNIĘTE** (było maskowaniem) |
| Silent pusty content zamiast failover | **NAPRAWIONE** (`provider_non_text_content`) |

### 5.2 Degradacja (świadoma) — wygląda jak maskowanie, ale ma log + trace

`pipeline.py` ma **~33** `except Exception` — typowy wzorzec:

```text
try: ciężka warstwa
except Exception:
    logger.debug/warning(...)
    ustaw flagę degraded / pomiń write-back
    kontynuuj turę
```

To **nie jest „user widzi OK przy totalnej awarii providera”** (provider errors lecą wyżej).  
To **jest** „V2 bridge padł → tura idzie bez V2, user nie wie”.  
Dla produkcji conversational: często pożądane. Dla observability: **dług** — za mało surface’owania w `errors[]` / SSE status.

Miejsca warte uczciwości:

- Meta/casual classifier wyjątek → wszystko `False` (ciężka ścieżka zamiast lekkiej) — rzadkie, ale realne.
- Deliberation fail → original response + `response_variants_error: true` — OK.
- Memory pack build fail → warning + `memory_context_pack_error` — OK jeśli trafia do debug/trace.

### 5.3 Frontend masking

- Composer przy błędzie przywraca draft tylko gdy pole puste — OK.
- Error boundary reload — hard reset, nie silent.
