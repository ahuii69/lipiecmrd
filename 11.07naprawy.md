## Regresja pełnego pytesta — root cause (11.07)

### Przyczyna główna

1. **Niezamykane połączenia SQLite** — `_conn()` zwracało `sqlite3.Connection` używane jako context manager transakcyjny, który **commituje**, ale **nie zamyka** połączenia. Przy ~980 testach i setkach wywołań `fetch_one`/`exec_one` na test rośnie liczba otwartych FD → `OSError: [Errno 24] Too many open files`, a wątki konsolidacji/workera mogły jeszcze dotykać starej ścieżki DB po usunięciu `tmp_path` → `sqlite3.OperationalError: unable to open database file`.

2. **Brak centralnego teardown** — fixture `isolated_db` wołała tylko `dispose_sqlite_engine()` z `except: pass`; worker konsolidacji, agent worker, singletony runtime i `TestClient` bez lifespan shutdown nie były zatrzymywane przed usunięciem katalogu testowego.

### Zasoby pozostające po teście (zidentyfikowane)

| Zasób | Objaw | Naprawa |
| ----- | ----- | ------- |
| Połączenia SQLite per `fetch_one`/`exec_one` | FD leak, locked DB | `@contextmanager _conn()` z `close()` w `finally` |
| `_ADAPTER_HOLDER` vs dispose race | operacje na usuniętej ścieżce | cache czyszczony **przed** WAL checkpoint; `active_sqlite_adapter_path()` |
| Consolidation daemon thread | późne zapisy V2 | `stop_background()` + `join(timeout=10)` |
| Agent worker `while True` | ticki po teście | `_stop_worker` Event + `stop_worker()` z join |
| `TestClient(app)` bez `with` | brak lifespan shutdown | fixture `client` używa context managera |
| Podwójny Psyche evolve | 2× update na turę | `TurnCompleted` przez `execute_turn_completed_inline` |

### FD / wątki (pomiar diagnostyczny)

- Przed resetem (typowy stan po teście): **~1 wątek** (`MainThread`), **~20–32 FD** (zależnie od importów).
- Po `reset_runtime_for_tests()`: **1 wątek**, **~20 FD** — stabilne w teście 100 cykli (`tests/test_runtime_resource_leak.py`).

## AUD-001 / AUD-002 — auth BFF + backend ownership (12.07)

### Problem (potwierdzone runtime)

- Anonimowy `curl :3001/api/aihub/memory/v2/summary/test-user` → **200** (BFF doklejał serwerowy klucz).
- Bezpośredni backend `:8080` → **401** (poprawnie).

### Naprawa

1. **BFF** — jawna polityka tras (`deny` by default), brak `x-api-key` / `x-aihub-proxy-token` dla anonimów, walidacja cookie `aihub_session` przez backend `/auth/me`, forward tylko podpisanego `x-aihub-principal`.
2. **Backend** — `auth_middleware`: public routes, signed principal HMAC (method+path+timestamp+nonce), ownership, CSRF tylko dla cookie (nie dla signed BFF).
3. **UI** — middleware redirect anon → `/login`; strona `/login`; `/admin` wymaga roli admin.
4. **Klient** — usunięto wysyłanie `x-aihub-api-key-override` ze stream/upload/STT.
5. **Deploy** — jeden stack systemd: backend **8080**, frontend **3001**; usunięto duplikat 8000/3000.

## Forbidden user scope + redesign chatu (13.07)

### Rzeczywista przyczyna `forbidden user scope`

Frontend generował **losowy** `user_id` w `localStorage` (`aihub-cockpit-user-scope-v1` → `u_<rand>_<ts>`) przez `ensureUserScope()` / `resolveScopedUserIdFromStorage()`.

BFF podpisywał request signed principal z **prawdziwym** `principal.user_id` z cookie sesji, ale body/path zawierały **stary/losowy** `user_id` → backend ownership: `403 forbidden user scope`.

Memory V2 „0 / error” i chaotyczne błędy w czacie były skutkiem tego samego mismatchu.

### Naprawa identity

- `GET /api/aihub/auth/me` → `principal.user_id` jako **jedyna** prawda (`useAuthPrincipal` + `bindAuthPrincipal`)
- Usunięto generowanie `u_*` z localStorage; klucz legacy jest czyszczony
- Store v7 migracja: reset sesji do bind z auth
- Chat / memory / psyche / upload używają `authUserId`

### UX chatu

- Usunięto stałą prawą kolumnę diagnostyczną (HUB/READY/DB/…)
- Pamięć w drawerze; status tylko „Połączono / Offline”
- Empty state: „O czym dziś pogadamy?”
- Friendly errors (401/403/502/network)
- Composer bez inline `style=` (CSP); `field-sizing: content`
- Sidebar zwijany + logout
