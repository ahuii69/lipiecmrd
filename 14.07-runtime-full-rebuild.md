# 14.07 — Runtime Full Rebuild

## 1. Stan przed

- `aihub/chat_runtime.py` = **6553 linii**, klasa `ChatRuntime` z **66 metodami**.
- Najcięższe metody: `_run_turn_core` (~1579), `_evaluate_blocker_verdict` (~600), `_pre_exec_decision_core` (~522), `_execute_agent_handoff` (~396).
- Orkiestracja HTTP → provider → tools → memory/psyche/experience/web/agent siedziała w jednym pliku.
- `turn_id` generowany **wiele razy** (experience write-back vs Memory V2 / Psyche V2).
- Idempotencja TurnCompleted istniała (`durable_jobs`), ale nie na poziomie całej tury HTTP.
- Specjalne ścieżki `user_id.startswith("audit_")` w produkcji.
- Provider: sniffing `TypeError` na sygnaturze `generate`.
- Brak cross-process locków per user/session.

## 2. Root causes

1. Monolit bez granic modułowych — każdy feature dopisywany do `ChatRuntime`.
2. Brak kanonicznego `TurnContext` / jednego `turn_id`.
3. Write-backi bez wspólnego idempotency key po stronie requestu.
4. Testowe haki po `user_id` zamiast jawnego `runtime_mode`.
5. Monkeypatchable symbole związane z modułem HTTP (wymagana fasada).

## 3. Graf starego runtime

```
POST /chat/turn → chat_api → get_chat_runtime().run_turn
  → ChatRuntime._run_turn_core
      → deterministic / memory-fact short-circuit
      → _build_context + V2 snapshots
      → _pre_exec_decision_core + blocker
      → controlled web prefetch
      → provider loop + tools / agent handoff
      → _write_back_experience (NOWY uuid)
      → Memory V2 + Psyche V2 write-back (DRUGI uuid)
      → transcript persist
```

## 4. Graf nowego runtime

```
POST /chat/turn → chat_api → ChatRuntime.run_turn
  → ChatTurnApplicationService.execute
      → begin_or_reuse_turn (idempotency_key)
      → session_turn_lock (PG advisory / SQLite lease)
      → TurnOps.run_turn_core  [aihub/turn/ops.py]
          → decision / web / provider / tools / handoff
          → write-backs z JEDNYM turn_id (active TurnContext)
      → complete_turn (succeeded|failed)
      → TraceBuilder fields: turn_id, request_id, correlation_id, runtime_mode
```

Pakiet `aihub/turn/`:
- `application.py` — entry + idempotency + lock
- `ops.py` — wyekstrahowana orkiestracja (dawny monolit)
- `models.py` — TurnContext, RuntimeEnvironment, typed results
- `errors.py` — typowana hierarchia błędów
- `idempotency.py` — turn_executions / turn_effects / outbox
- `concurrency.py` — session lock
- `provider_service.py` — timeout/retry/classification (bez TypeError sniff)
- `tool_service.py` — args parse, limits, side-effect idempotency
- `completion.py` — exactly-once effects
- `trace.py` — TraceBuilder + redaction

`chat_runtime.py` = cienka fasada (`ChatRuntime(TurnOps)` + ApplicationService).

## 7. Model idempotencji

- Klient wysyła `idempotency_key` (frontend generuje UUID na send, retry reuse).
- Serwer: `begin_or_reuse_turn` → przy `succeeded` zwraca cached `ChatTurnResult`.
- Efekty: `claim_effect` / `finish_effect` — drugi raz = skip.
- `durable_jobs.TurnCompleted` nadal działa, ale z **tym samym** `turn_id`.

## 8. Model concurrency

- `session_turn_lock(user_id, session_id)` — serializacja tur tej samej sesji między procesami.
- Postgres advisory lock; SQLite tabela lease.
- Process-local `threading.Lock` tylko jako zagnieżdżony guard.

## 9. Timeout / retry policy (provider)

- connect/read/total z `RuntimeEnvironment`
- retry tylko transient (timeout, 429, 5xx)
- exponential backoff + jitter + Retry-After
- **bez** TypeError signature sniffing
- `ProviderError` z providera przepuszczany do istniejącego fallbacku

## 10. Tool execution policy

- parse: dict / JSON string / empty / malformed / non-object
- limity: round / turn / argument bytes / result bytes / timeout
- side-effect tools: effect slot `tool:{name}:{tool_call_id}`

## 11. Write-back / outbox

- Memory V2 + Psyche V2 + experience/durable używają `TurnContext.turn_id`
- `turn_outbox` gotowy do recovery workera
- `runtime_mode=audit` wyłącza write-backi (NIE `user_id`)

## 12. Streaming lifecycle

- Bez zmiany kontraktu SSE (`chat_api` + `ChatStreamSession`)
- Disconnect nadal canceluje task workera
- Final event / error path bez zmian API

## 13. Trace / redaction

- `TraceBuilder` schema `turn-trace-v1`
- Redakcja: authorization, cookies, api keys, passwords, vault, tokens
- Tool results w trace: summary (bytes, sha256, preview) — nie full payload by default

## 18. Znane ograniczenia

1. `TurnOps` (`ops.py`) nadal jest dużym plikiem etapów — odpowiedzialność orkiestracji jest już poza HTTP facade; dalszy split etapów (decision/web/execution) możliwy bez zmiany kontraktu.
2. Outbox recovery worker nie jest osobnym systemd unit — schema + claim API są gotowe; inline completion pokrywa happy path.
3. Login/register UI poza zakresem rebuildu runtime.
4. Nazwa `execution_mode` w `decision_core` (direct/planner) **pozostaje** — tryb zaufany to `runtime_mode`.
