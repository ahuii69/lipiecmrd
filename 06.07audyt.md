## 1. Executive Summary

- **Projekt uruchamia się — POTWIERDZONE.** Aktywny backend działa jako `/home/ubuntu/.venvs/mrd-312/bin/python -m uvicorn aihub.main:app --host 127.0.0.1 --port 8000 --workers 1`; frontend jako `next-server v15.5.14` na `*:3000`. `GET :8000/system/ping` i `GET :8000/ops/ready` zwróciły 200, readiness `ready=true`.
- **Backend działa — POTWIERDZONE.** 91 aplikacyjnych par metoda/ścieżka plus 4 trasy dokumentacji są zgodne z `aihub/canonical_http_surface.py:53-72,105+`. Pełny pytest: **962 passed, 1 skipped**.
- **Frontend buduje się i odpowiada — POTWIERDZONE.** `npm run typecheck`, `npm run build`, `npm run lint` i 66 testów Vitest zakończyły się powodzeniem; `/` i `/user` zwracają 200.
- **Główny chat pipeline jest realny, ale bezpieczny audyt nie wykonał nowej płatnej tury.** Kod prowadzi przez `chat_api.chat_turn` → `ChatRuntime.run_turn/_run_turn_core` → DeepInfra → narzędzia → write-back. Logi aktywnego wdrożenia zawierają udane `V2 chat write-back: memory=True psyche=True` (`logs/aihub.log:7147,7522,7597`). Pełnej jakości odpowiedzi aktualnego modelu oznaczono `BRAK DANYCH DO POTWIERDZENIA`, ponieważ nowa tura zapisałaby dane i zużyła płatny provider.
- **Operatorskie capability API jest zepsute — POTWIERDZONE RUNTIME.** Każde `POST /chat/capabilities/execute` kończy się 500 przed uruchomieniem narzędzia: model ma pole `policy_overrides`, handler odczytuje nieistniejące `payload.tool_policy_overrides` (`aihub/chat_api.py:37-45,277-314`). Izolowana próba `memory.search` zwróciła HTTP 500.
- **Memory Engine działa częściowo.** V1 i V2 zapisują do SQL; V2 lexical+dense retrieval, FAISS, outbox indeksowania, context pack i write-back są realne i przeszły izolowany smoke. Nie ma BM25; okresowy `run_decay_pass` jest niewpięty; aktywny worker konsoliduje domyślnie tylko użytkownika `default`; FAISS jest globalnym plikiem bez blokady i ma problem recall między użytkownikami.
- **Psyche działa częściowo.** V1 oraz V2 są per-user i trwałe w SQL, a ich kontekst wpływa na prompt/strategię. Zwykła tura wykonuje jednak **podwójną ewolucję Psyche V1** i **podwójny zapis reflection**. Dreams, rage, depression i autonomiczna mutacja osobowości nie mają pełnego łańcucha runtime.
- **Web działa realnie.** SSRF guard, limity, redirect validation, ekstrakcja HTML, Brave/Wikipedia/DDG, ranking i wpięcie do chatu istnieją. Aktualny health oznacza web research jako aktywny. Brak robots.txt, pełnej weryfikacji twierdzenie↔cytat i bezpiecznej automatycznej kuracji web-learning.
- **Dane są trwałe**, gdy działa PostgreSQL/SQLite oraz pliki FAISS. Trwałość nie oznacza jednak poprawnej wielodzierżawności: identyfikator użytkownika jest wartością podawaną przez klienta, bez tożsamości użytkownika.
- **System nie nadaje się do produkcji.** Krytyczne blokery: publiczny BFF automatycznie dokleja serwerowy API key, brak logowania/tożsamości i IDOR, publiczne cache’owanie odpowiedzi API przez rok, profil `ENV=development`, brak supervisora/TLS/CI, kosztowne publiczne health-checki oraz race conditions plikowego FAISS.
- **Realne ukończenie funkcjonalne: 68%. Gotowość produkcyjna: 34%.** Metoda punktacji jest w §33.

## 2. Końcowy werdykt

**DZIAŁAJĄCY, ALE NIEPRODUKCYJNY.**

To nie jest atrapa: backend, frontend, PostgreSQL, Voyage, FAISS, web, Psyche, Memory V2, worker agenta i worker konsolidacji działają w bieżącym procesie; testy i build przechodzą. Nie jest to jednak system produkcyjny, bo:

1. `cockpit/app/api/aihub/[...path]/route.ts:64-76,116-163` dodaje serwerowy sekret każdemu anonimowemu klientowi BFF. Dowód runtime: bez klucza `:8000/memory/v2/summary/...` zwraca 401, ta sama ścieżka przez `:3000/api/aihub/...` zwraca 200.
2. `user_id` pochodzi z klienta (`cockpit/lib/store/cockpit-store.ts`, `cockpit/lib/api/client.ts:45-50,148-153,186-221`) i nie jest związany z uwierzytelnioną tożsamością. To pozwala czytać/modyfikować cudzą pamięć, psyche, sesje i cele.
3. `cockpit/next.config.mjs:53-80` nakłada `Cache-Control: public, max-age=31536000, immutable` na wszystkie odpowiedzi, również BFF. Potwierdzono ten nagłówek na `/api/aihub/memory/v2/summary/...`.
4. Wdrożenie działa przez procesy `nohup`, bez aktywnej jednostki systemd, reverse proxy i TLS; backend jest wprawdzie na loopback, ale frontend nasłuchuje na wszystkich interfejsach.
5. Aktualny `.env` ma `ENV=development`; brakuje `AIHUB_USER_VAULT_KEY`, a walidacja produkcyjna oczekuje `DEEPINFRA_API_KEY`, choć runtime korzysta z ustawionego `LLM_API_KEY` (`aihub/config.py:102-143,207-210`).

## 4. Architektura rzeczywista

```text
Przeglądarka
  -> Next.js 15 :3000 (publiczny UserShell)
     -> catch-all BFF /api/aihub/*
        -> allowlista metoda+ścieżka
        -> automatyczne x-api-key + x-aihub-proxy-token
        -> FastAPI/Uvicorn :8000 na 127.0.0.1
           -> globalny middleware API-key
           -> chat_api / agent_api / memory_v2_api / psyche_v2_api / cockpit_api
           -> ChatRuntime (centralny monolit)
              -> MemoryCanonicalCore -> Memory V1 SQL + Memory V2 SQL/FAISS
              -> PsycheCanonicalCore -> Psyche V1 + Psyche V2
              -> Strategy/Decision/Executive/Tool Registry
              -> ResearchEngine/WebTools
              -> DeepInfra OpenAI-compatible API
              -> transcript, event_log, reflection, write-back
           -> PostgreSQL (aktywny profil) / SQLite (test i fallback)
           -> plikowy FAISS + JSON metadata
           -> wątki: agent worker + Memory V2 consolidation
```

Rzeczywisty kanon HTTP to `aihub.main:app`, nie wszystkie pliki z `aihub/api/`. `main.py:202-210` montuje dziewięć routerów. Pakiety `aihub/memory/` i `aihub/psyche/` są osobnymi, działającymi, ale niewpiętymi stosami legacy (`_LEGACY.md`). Frontend produkcyjny nie używa operatorskiego `AppShell`; oba route’y renderują `UserShell`.

## 6. Pełny graf przepływu requestu

1. `UserShell` (`cockpit/features/user-chat/user-shell.tsx`) tworzy `ChatTurnPayload`; uploady idą przez `chat-upload.ts`, streaming przez `chat-turn-stream.ts`.
2. `fetch("/api/aihub/chat/turn")` trafia do BFF (`route.ts:116-188`), który sprawdza allowlistę, dodaje hub key i forwarduje stream.
3. `main._auth_middleware` (`main.py:175-199`) akceptuje proxy token/API key. Nie ustala principal/user identity.
4. Pydantic waliduje `ChatTurn` w `chat_api.py`; `chat_turn`/`_sse_chat_turn` wywołuje `get_chat_runtime().run_turn`.
5. `ChatRuntime._run_turn_core` ładuje transcript, klasyfikuje intent, secret/vault path i tryby deterministyczne.
6. `runtime_memory_bridge`/`memory_core.retrieve_unified` pobiera V1 STM/LTM i V2 hybrid/context pack; wynik trafia do trace i promptu.
7. `runtime_psyche_bridge.build_psyche_v2_behavior_context` oraz V1 psyche kształtują system prompt, strategię i guardy.
8. Decision/strategy wybiera direct LLM, controlled web prefetch, agent handoff lub tool loop.
9. `_build_system_prompt` składa politykę produktu, historię, pamięć, psyche, web evidence, attachment context i instrukcje narzędzi.
10. `_provider_call` tworzy `ProviderChatRequest`; `DeepInfraProvider.generate` robi async HTTP, retry/backoff, streaming bez tools lub non-stream z tools.
11. Tool calls są walidowane/routowane przez `aihub/tools/router.py` i registry; wynik wraca do kolejnej wiadomości modelu.
12. Persona/anti-hallucination/grounding guard modyfikuje lub blokuje odpowiedź.
13. Transcript i event trace są zapisywane.
14. `MemoryCanonicalCore.ingest_turn` zapisuje STM/fakty/epizod i sam wywołuje Psyche V1; potem runtime ponownie wywołuje `_psyche_evolve_fn` — podwójny side-effect.
15. `record_chat_outcome` zapisuje Memory V2 i `PsycheV2Service.record_chat_outcome`; `_post_exec_reflection` zapisuje reflection, a ingest path zapisuje drugie.
16. SSE przekazuje eventy/final do frontendu; UI aktualizuje Zustand i odświeża historię/panele.

Wpływ na finalną odpowiedź:

- Memory: **TAK**, context pack jest częścią promptu i trace.
- Psyche: **TAK**, behavior context wpływa na system prompt/strategię/persona guard.
- Web: **TAK warunkowo**, evidence jest w prompt; dla trybu web-required brak evidence kończy turę kontrolowanym komunikatem.
- Reflection/write-back: wpływa dopiero na późniejsze tury; bieżąca odpowiedź jest już wygenerowana.

## 10. Audyt LLM i prompt pipeline

- Jedyny zarejestrowany provider to DeepInfra (`provider_registry.py:62-71`). Nazwa „registry” nie oznacza realnego multi-provider failover.
- `DeepInfraProvider.generate` ma timeout, retry dla 408/409/425/429/5xx, exponential backoff i normalizację błędów (`deepinfra_provider.py:429-508`).
- Streaming jest prawdziwy dla tur bez tools (`315-427`), ale gdy tools istnieją, kod jawnie ustawia `stream=false` (`453-455`). UI nadal używa SSE, lecz w takim przypadku może otrzymać dopiero wynik po pełnym callu.
- `ProviderChatRequest.max_tokens` ma limit kontraktowy 32768, ale runtime przekazuje `None`; provider wtedy pomija `max_tokens` (`provider_types.py:23-34`, `deepinfra_provider.py:434-445`). Koszt/rozmiar zależy od defaultu providera.
- Usage tokens są parsowane, gdy provider je zwraca; brak budżetów kosztowych, billing aggregation i alertów.
- Prompt zawiera memory/psyche/web/history/attachments i tool policy. Duża liczba warstw w jednym `_build_system_prompt` zwiększa ryzyko konfliktów oraz prompt injection.
- Potwierdzenie mutujących narzędzi nie ma zaufanego źródła: `ToolRouter.execute` uznaje `call.arguments["_confirmed"]` za decyzję człowieka (`tools/router.py:130-137`), a w zwykłym tool loop argumenty tworzy model. Przy trybie/policy dopuszczającym mutację model może sam ustawić `_confirmed=true`; human-in-the-loop jest obchodzony.
- Provider errors prowadzą do jawnego fallback/degraded response, nie do fałszywego sukcesu, ale częściowe błędy write-back są tylko logowane i odpowiedź może wyjść jako sukces.
- Embedding provider używa synchronicznego `requests.post` wewnątrz async chat flow, co blokuje event loop.
- Aktualny `/ops/health` dla LLM sprawdza konfigurację i TCP, a nie poprawność klucza ani realną completion (`ops_platform.py:163-188`). Status `llm=ok` nie jest dowodem generacji.

## 13. Audyt baz, storage, embeddings i cache

### SQL

- Aktywny profil to PostgreSQL; port 5432 nasłuchuje, `/ops/ready` potwierdza DB.
- Testy są hermetyczne i używają SQLite temp (`tests/conftest.py`).
- Schemat jest tworzony/uzupełniany w runtime przez `aihub/db/runtime.py` oraz bootstrap/import scripts, nie przez wersjonowany system migracji typu Alembic. Ryzyko: drift i trudny rollback.
- Parametry SQL są bindowane, nie znaleziono aktywnego SQL injection.
- PostgreSQL i SQLite są wspierane przez adapter placeholderów, lecz **aktywny kod nadal zawiera błąd PostgreSQL**: `memory_v2_repository.reinforce_memory_item` używa skalarnego `MIN(1.0, recurrence_score + ?)` i `MIN(1.0, salience_score + ?)` (`memory_v2_repository.py:297-324`). PostgreSQL wymaga `LEAST`; istniejące logi potwierdzają `function min(numeric, double precision) does not exist`. `record_chat_outcome` łapie błąd wyżej, więc odpowiedź może wyjść, ale reinforcement nie działa. Ten sam wzorzec w `meta_memory.py:59-78` jest wyciszany na DEBUG.
- Równoległy legacy schema stack `aihub/db/database.py`, `sqlite.py`, `schema.py` obsługuje niewpięte `aihub/memory/`/`psyche/`.

### Vector/embeddings

- Produkcja: Voyage `voyage-4-large`, output 1024; live probe bez fallbacku potwierdzony w logach.
- FAISS `IndexFlatL2` jest trwały, ale nie ma transakcji wspólnej z SQL ani JSON meta. Crash między `index.add`, meta append i `_save` może rozjechać pozycje.
- Brak locków między requestami/wątkami oraz atomic file replace.
- Search filtruje usera po globalnym nearest-neighbor fetch; izoluje treść, ale nie zapewnia recall.
- Nie ma delete/update/compaction wektorów; archiwizacja w SQL nie usuwa wektora.

### Cache

- Nie ma Redis ani rozproszonego cache/queue.
- In-process cache istnieje dla providerów/dimension oraz modułów.
- Frontendowy HTTP cache jest skonfigurowany niebezpiecznie globalnie na rok.

### Backup/recovery

Są skrypty backup SQLite i snapshot/restore endpointy. Brak potwierdzonego automatycznego backupu PostgreSQL, retencji, restore drill i spójnego backupu SQL+FAISS: `BRAK DANYCH DO POTWIERDZENIA`.

## 20. Błędy runtime

1. `POST /chat/capabilities/execute` zawsze zwraca 500: `CapabilityExecuteInput.policy_overrides` kontra `payload.tool_policy_overrides`; błąd jest przed `try`.
2. Anulowanie SSE może rzucić wtórny `NameError`, bo `chat_api.py:132` używa niezdefiniowanego `logger`; reset contextvara nie dojdzie do skutku.
3. Aktywny PostgreSQL reinforcement używa niekompatybilnego `MIN(a,b)`; Memory V2 learning kończy się błędem przechwyconym wyżej.
4. Podwójne V1 psyche evolve i reflection per normal chat.
5. NumPy vector fallback nie zapisuje `.npy` z powodu nazwy backendu.
6. FAISS race/index-meta inconsistency bez locków.
7. Multi-user vector recall przez filtrowanie po globalnym top-k.
8. Publiczny BFF uzyskuje dostęp do chronionych endpointów anonimowo.
9. Publiczne health/capabilities wykonują live Voyage/Brave/STT probes. Przy `EMBEDDING_HEALTHCHECK_LIVE_PROBE=1` każde wywołanie może kosztować i blokować; endpoint jest w `NO_AUTH_PATHS`.
10. LLM readiness może być `ok` przy nieważnym kluczu, bo robi tylko TCP.
11. Worker consolidation nie obejmuje dynamicznych user IDs.
12. Sync Voyage embedding blokuje async event loop.
13. `Cache-Control` dla dynamicznego API jest public/immutable.

## 23. Problemy wydajnościowe i skalowalność

- `chat_runtime.py` >6389 linii i wykonuje wiele sekwencyjnych DB/provider stages.
- Synchroniczne Voyage `requests.post` blokuje async worker.
- Jeden Uvicorn worker; zwiększenie workers duplikuje background threads i pogarsza FAISS race.
- `IndexFlatL2` ma liniowe wyszukiwanie; brak ANN/sharding.
- Każdy vector add zapisuje cały indeks i cały JSON meta.
- Search pobiera globalne `5*k`, dopiero potem filtruje user.
- `embed_batch` jest sekwencyjny (`embedding_engine.py:530-557`).
- SSE event log max 50 000 in-memory może rosnąć.
- Memory V2 SQL ma indeksy, ale runtime health wykonuje wiele zapytań i zewnętrznych probe na request.
- Brak Redis/cache/queue; każdy proces ma własne cache i worker state.
- Brak connection-pool telemetry i load testów produkcyjnych: `BRAK DANYCH DO POTWIERDZENIA`.

## 24. Problemy obserwowalności

POTWIERDZONE:

- rotowane logi z modułem/funkcją/linią (`aihub/logs.py`);

- `/ops/health`, `/ops/ready`, `/ops/capabilities`;

Braki:

- brak Prometheus/OpenTelemetry/Sentry/Datadog;
- brak correlation ID generowanego konsekwentnie na wejściu;
- brak distributed trace BFF→backend→provider→DB;
- brak metryk p95, error rate, token cost, queue lag, worker heartbeat;
- brak alertingu;
- readiness miesza health, kosztowne live probe i mutujący `ensure_user`;
- logi historycznie zawierają user IDs; polityka PII/retencji nie jest zdefiniowana;
- sukces HTTP nie ujawnia częściowego failure write-back poza debug trace/logiem.

## 35. Rekomendowana architektura docelowa

```text
TLS reverse proxy
  -> Next UI
     -> authenticated server session (OIDC)
     -> BFF derives principal; never exposes/shared hub key
        -> FastAPI
           -> AuthN middleware + per-route AuthZ policy
           -> Chat Application Service (phase pipeline)
              1 context read (Memory V2, Psyche V2)
              2 decision/web/tools
              3 provider gateway (multi-provider, budgets)
              4 response guards
              5 transactional outcome event
           -> PostgreSQL as system of record
           -> pgvector or isolated vector service
           -> durable queue (index, consolidation, decay, reflection)
           -> workers with leases/idempotency
           -> OTEL metrics/traces/logs
```

Memory V2 i Psyche V2 powinny być jedynymi zapisywalnymi modelami. V1 pozostawić tylko jako adapter migracyjny/read-only do czasu migracji danych. Reflection, memory i psyche write-back powinny konsumować jeden `TurnCompleted` event z idempotency key. Web evidence musi być danymi oznaczonymi jako untrusted, nie instrukcjami. Operatorski AppShell powinien być osobną, chronioną rolą.
